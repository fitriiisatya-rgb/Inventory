Built on approval of Phase G-DATA 1B.3 (baseline: `unit_conversion_review_v5.xlsx`,
1,165 SKU, 0 `CONVERSION_CONFLICT`, 0 `CROSS_COUNT_UNIT`, 34 `BUSINESS_CONFIRMED`
conversions, 82/82 regression). This phase builds the **tooling** for final
opening stock import — it does **not** import any real opening data. No
owner-verified final stock file has been supplied yet.

`migration/templates/final_opening_stock_template.xlsx` (generated by
`migration/scripts/generate_final_opening_stock_template.py`) — 2 sheets:

- **INSTRUCTIONS** — the Global Base Unit / LOW-confidence policy, unit-cost

- **Template** — the 14 requested columns (Cutoff Date, Warehouse Code, SKU,

  dropdown validation (SCM/CIBADAK/KARANG_TENGAH).

## 2. Validation result

New `services/OpeningValidationService.php`, called from
`ImportOpeningStockService::stage()`:

**ERROR** (blocks commit for that batch until fixed): unknown SKU, unknown
warehouse, negative quantity, positive quantity with cost ≤ 0
(`COST_REQUIRED`), Global Base Unit mismatch against the item master,
invalid Expiry Date, duplicate warehouse+SKU+batch_reference within the same
upload, inconsistent Cutoff Date across rows (checked once, batch-level,
before the header is even created).

**WARNING** (never blocks): zero quantity, very large quantity (>1,000,000),
unit cost differing materially from the trusted reference
(`PriceAnomalyService`, reused as-is), missing category (`NEEDS_CATEGORY`),
and — the central policy — **no approved purchase conversion**. This last
one is explicitly informational: opening always posts in the item's Global
Base Unit, so a missing/LOW-confidence purchase-unit conversion never
blocks it.

Verified live end-to-end against the real template file (not just synthetic

confirmed every column (including the new audit columns) landed correctly,

## 4. API / UI changes

- **New error code `UNIT_CONVERSION_NOT_APPROVED`** (422) — a new
  `UnitConversionNotApprovedException`, thrown by `FifoService::postIn`/
  `postOut` in place of the old generic `VALIDATION_ERROR` whenever no
  active `item_unit_conversions` row exists for the requested unit.
  Documented in `docs/API_CONTRACT.md`.
- **`GET /items/{id}/units` already existed** (built in an earlier phase)
  and **already only returns units with an active, approved conversion**
  (`item_unit_conversions WHERE valid_to IS NULL`). The Transaction IN/OUT
  frontend (`public/assets/js/transactions.js`) already populates its unit
  dropdown exclusively from this endpoint. **No frontend change was needed**
  to satisfy "UI must not offer an unapproved purchase unit" — that
  contract was already enforced by construction. Verified by reading the
  existing route and the frontend call site, not assumed.
- **New `GET /import/opening-stock/{id}/reconciliation`** — the
  GO_LIVE_READY checklist (Section 12/15 below).
- **New `GET /movement-reconciliation-reviews`** — the 8 historical rows,
  read-only.
- Not built this round: a dedicated admin screen for browsing
  `unit_conversion_candidates` (the "may still view candidate conversion in
  Master/Review screen" allowance) — currently only visible via the
  `unit_conversion_review_v5.xlsx` workbook. Flagged as a real gap, not
  silently skipped.

## 5. How LOW-confidence conversions are handled

Exactly per Section 1: a SKU with no approved purchase-unit conversion (or
only a LOW-confidence candidate) can still have its item created, its
opening stock posted, and normal base-unit transactions posted — none of
that path ever consults `item_unit_conversions` for anything except the
identity (base-unit, factor 1) row, which every item gets automatically at
creation (`ImportMasterItemService`). The **only** thing that's blocked is
transacting in a *different*, unapproved unit (e.g. CTN) — that now fails
fast with `UNIT_CONVERSION_NOT_APPROVED` instead of a generic validation
error, and the UI's unit dropdown was already incapable of offering that
unit in the first place (see Section 4).

The 34 `BUSINESS_CONFIRMED` conversions from Phase G-DATA 1B.1/1B.3 are
loaded into the `unit_conversion_candidates` staging table (schema now
extended with `conversion_source`, `admin_source_answer`,
`prior_detector_evidence`, `approved_by_name` — nothing deleted, full audit
preserved) via `scripts/load_approved_conversions_v5.php` — verified: 34/34
loaded, spot-checked 999208/999209/140539 match exactly. A **separate**
script, `scripts/promote_approved_conversions.php`, would write these into
the real `item_unit_conversions` table — it was written and dry-run tested
(`--dry-run`), but **not executed for real**, since it requires the item to
already exist by SKU and the real item master has not been imported. It
correctly reports "SKIP — item does not exist yet" for all 34 rows when
run against the current (empty) `items` table — confirmed live.
